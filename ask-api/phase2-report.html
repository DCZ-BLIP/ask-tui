02 AI 服务 — GLM-4-Flash 集成

2.1 Prompt 工程

系统提示词（SYSTEM_PROMPT）将 GLM-4-Flash 定位为命令行助手，要求严格输出 JSON 格式，包含四个字段：

  • thinking — 对用户需求的理解（1-2 句中文）
  • command — 可直接执行的 shell 命令
  • explanation — 命令参数的详细解释
  • danger_level — 危险等级：safe / warn / danger

危险等级判定标准明确写入 prompt：只读操作为 safe，可恢复修改为 warn，不可逆操作为 danger。

2.2 流式调用

chat_completion_stream() 使用 httpx 异步流式请求智谱 API，逐块 yield 增量文本，解析 SSE 格式的 data: 行，遇到 [DONE] 终止。同时提供非流式方法 chat_completion() 作为备用。

2.3 响应解析与容错

parse_ai_response() 对 AI 输出做三层容错：

  • 移除可能的 markdown 代码块包裹（```json ... ```）
  • 标准 JSON 解析，缺失字段填充默认值
  • 解析失败时降级为纯文本 explanation，danger_level 默认 safe
设计决策：选择 GLM-4-Flash 而非其他模型，因为智谱提供免费额度，且模型对 JSON 格式指令的遵守度高。temperature 设为 0.3 以降低随机性，max_tokens 1000 足够覆盖绝大多数 shell 命令场景。

03 流式聊天路由 — SSE 事件流

POST /api/chat 接口通过 Server-Sent Events 向客户端推送 AI 响应。完整事件序列如下：

start 开始事件，携带 user_message_id
chunk 增量文本块（多次发送，逐块拼接） → chunk → chunk
result 结构化结果：thinking / command / explanation / danger_level / message_id
done 结束事件

3.1 关键实现细节

  • 设备鉴权：通过 X-Device-ID 头识别用户，未激活返回 401
  • 对话归属验证：检查 conversation_id 是否属于当前用户，不存在返回 404
  • 用户消息持久化：在 SSE 流开始前保存用户消息并 commit
  • 上下文构建：从数据库加载完整对话历史，拼装为 system + history 的 messages 列表
  • AI 消息保存：SSE 流结束后用独立 session 保存 AI 消息（避免与请求 session 冲突）
  • 错误处理：任何异常都通过 error 事件返回，不中断连接

3.2 多轮对话上下文

每次请求时从数据库加载该对话的全部历史消息，构建为 OpenAI 兼容的 messages 列表传入 AI。assistant 消息使用原始 JSON 字符串作为 content，让模型理解之前的回复上下文。

04 中间件层

4.1 限流中间件

rate_limit_middleware 拦截所有 /api/chat 请求，按设备 ID + 日期进行计数。内存存储 _rate_store 结构为 {device_id: {date_str: count}}，每日自动滚动。超过 DAILY_REQUEST_LIMIT（默认 200 次）返回 429。

  • 只限制 /api/chat，其他接口不受影响
  • 内存存储，应用重启后重置（对免费部署足够）
  • 可通过 RATE_LIMIT_ENABLED 开关全局关闭
  • 提供 reset_rate_store() 和 get_device_usage() 供测试使用

4.2 管理员鉴权

require_admin 是一个 FastAPI 依赖，通过 X-Admin-Key 头校验管理员身份。密钥存储在 settings.ADMIN_API_KEY，用于保护邀请码生成等管理接口。密钥不匹配返回 403。

05 消息清理调度器

cleanup_scheduler() 是一个 asyncio 后台任务，在应用启动时通过 lifespan 创建，随应用关闭时取消。每 CLEANUP_INTERVAL_HOURS（默认 24 小时）执行一次，删除创建时间超过 MESSAGE_RETENTION_DAYS（默认 7 天）的消息。

# main.py 中的启动逻辑
@asynccontextmanager
async def lifespan(app: FastAPI):
    await init_db()
    cleanup_task = asyncio.create_task(cleanup_scheduler())
    yield
    cleanup_task.cancel()
注意：调度器启动后先等待一个完整周期再首次执行，避免启动时立即触发清理。清理操作的错误通过 print 输出，不影响后续调度。

6.3 ApiClient 设计

所有 HTTP 交互封装在 ApiClient 类中，使用 httpx 异步客户端。关键方法：

  • activate(invite_code, username) — 邀请码激活
  • get_user() — 检查是否已激活（连接失败返回 None）
  • list_conversations() / create_conversation() / delete_conversation() — 对话 CRUD
  • get_messages(conv_id) — 获取对话历史
  • chat_stream(conv_id, content) — SSE 流式聊天，yield 事件字典

6.4 命令预览渲染

右侧面板使用 Rich 库渲染命令预览：

  • Syntax(command, "bash", theme="monokai") 语法高亮
  • 危险等级颜色映射：safe→green, warn→yellow, danger→red
  • Panel 包裹，border_style 随危险等级变化
  • 包含 thinking 和 explanation 的中文说明

8.1 SSE 测试策略

聊天接口测试通过 unittest.mock.patch mock 掉 chat_completion_stream，避免依赖真实 AI API。模拟三种 AI 响应场景：

  • 正常 JSON：分两块 yield 完整 JSON，验证事件序列和结果字段
  • 危险命令：返回 danger 级别命令，验证 danger_level 传递
  • 非 JSON 降级：返回纯文本，验证 command 为空、降级为 explanation

8.2 限流测试

通过 monkeypatch 将 DAILY_REQUEST_LIMIT 设为 2，连续发送 3 次请求，验证第三次返回 429 和"上限"提示。

8.3 多轮上下文测试

模拟两轮对话，通过 mock 捕获 AI 收到的 messages 列表，验证第二轮请求包含 system + 第一轮 user + 第一轮 assistant + 第二轮 user 的完整上下文。

10 下一步计划

第 2 阶段已完成核心功能闭环（后端 AI 集成 + TUI 客户端交互）。第 3 阶段建议方向：

  • 部署上线：将 ask-api 部署到免费平台（如 Render / Railway），配置智谱 API Key
  • 命令执行：TUI 端实现本地命令执行功能，带安全确认弹窗（danger 级别需二次确认）
  • 打包分发：用 PyInstaller 将 ask-tui 打包为单文件可执行程序，分发给朋友
  • 用户体验：加载动画、错误重试、离线提示、对话搜索
  • 安全加固：命令注入检测、敏感目录保护、操作日志审计
